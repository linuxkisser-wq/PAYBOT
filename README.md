# Бот поддержки Nexora Pay

Анонимный прокси между пользователями и администратором. Пользователь общается
с «Поддержкой Nexora Pay» и не знает, что за ботом живой человек.

Стек: Python 3.11+, aiogram v3, PostgreSQL, asyncpg, python-dotenv.

## Запуск

```bash
python -m venv .venv
.venv\Scripts\activate        # Windows
pip install -r requirements.txt

copy .env.example .env        # заполнить токен и пароли
docker compose up -d db       # создать и запустить PostgreSQL
python bot.py
```

Нужен установленный Docker Desktop с Compose. При первом запуске контейнера
создаются отдельный пользователь приложения (`DB_USER`) и база (`DB_NAME`).
Дальше данные сохраняются в Docker volume `postgres_data`. Бот создаёт таблицы
и индексы при старте и подключается через пул соединений.

`DATABASE_URL` — адрес подключения к базе в формате
`postgresql://пользователь:пароль@хост:порт/имя_базы`. Например,
`postgresql://nexora:пароль@localhost:5432/nexora_support`. В шаблоне URL
собирается из `DB_USER`, `DB_PASSWORD` и `DB_NAME`. Пароль в URL должен быть
URL-кодирован, если содержит специальные символы.

`POSTGRES_ADMIN_PASSWORD` нужен только для начальной настройки контейнера;
бот подключается как отдельный пользователь с правами только на свою базу.
Инициализация запускается лишь для пустого Docker volume. Если volume уже
существует, смена переменных в `.env` не меняет существующие пароль и базу.

`BOT_TOKEN` — у [@BotFather](https://t.me/BotFather). `ADMIN_CHAT_ID` — свой ID
у [@userinfobot](https://t.me/userinfobot); для группы ID отрицательный
(`-100...`), и бота нужно добавить в группу.

Лог (`bot.log`) создаётся автоматически при первом запуске. SQLite-файл от
предыдущей версии остаётся нетронутым и автоматически не переносится в PostgreSQL.

## Структура

| Файл | Назначение |
| --- | --- |
| `bot.py` | точка входа, логирование, фоновая задача таймаутов |
| `config.py` | чтение `.env` |
| `db.py` | схема PostgreSQL и весь доступ к данным |
| `services.py` | операции над тикетами, общие для обоих роутеров |
| `handlers/user.py` | FSM создания заявки + активный чат |
| `handlers/admin.py` | приём/отклонение, ответы, закрытие |
| `keyboards.py` | inline-клавиатуры |
| `texts.py` | все тексты и категории обращений |

## Команды

Пользователь: `/start` · `/status` · `/history` · `/cancel`

Администратор (только в `ADMIN_CHAT_ID`): `/tickets` · `/stats` · `/reply 1` · `/stop [1]` · `/help`

## Как это работает

**Пользователь:** `/start` → кнопка «Создать заявку» → причина → описание
(минимум 10 символов) → фото (опционально) → карточка подтверждения → отправка.
Каждый шаг подписан прогресс-баром (`▰▰▱▱ Шаг 2 из 4`).
Номер выдаётся на шаге подтверждения и не меняется при нажатии «Изменить».

Нумерация идёт с `#0001` (счётчик стартует с нуля, ведущие нули — для вида).

**«Изменить»** открывает меню точечной правки: причина, описание, фото —
каждое поле правится отдельно и сразу возвращает к карточке, без прохода
всего флоу заново.

**После закрытия тикета** пользователю приходит запрос оценки (⭐ 1–5).
Оценка пишется в `tickets.rating`, уходит админу и попадает в `/stats`.

**Администратор:** получает карточку с кнопками «Принять» / «Отклонить».
Принятие редактирует карточку и открывает чат. Отклонение удаляет карточку
и запрашивает причину текстом — она уходит пользователю.

**Переписка:** сообщения пользователя приходят админу с пометкой `[👤 User #1001]`,
ответы админа уходят пользователю от имени бота, без каких-либо следов отправителя.

**Таймаут и SLA:** фоновая задача раз в минуту напоминает админу о заявке,
висящей дольше `SLA_PING_MINUTES` (30 мин, ровно один пинг на заявку), и
помечает нерассмотренные заявки старше 24 часов как `expired` с уведомлением
пользователя. Состояние живёт в БД, так что и то и другое переживает
перезапуск бота.

**Статистика (`/stats`):** количество заявок по статусам, среднее время до
принятия, средняя оценка и топ-3 причины обращений.

## Прокси

Если провайдер режет `api.telegram.org`, задай `PROXY_URL` в `.env`
(например `http://127.0.0.1:10801`). Пустое значение = взять системный прокси
из `HTTPS_PROXY`/`ALL_PROXY`, если он там есть. Для прокси нужен пакет
`aiohttp-socks` — он уже в `requirements.txt`. На сервере без блокировок строку
можно оставить пустой.

## Решения, которые пришлось принять

Три места в ТЗ допускали разные прочтения — вот что выбрано и почему.

**Несколько активных тикетов одновременно.** ТЗ говорит «один активный тикет на
пользователя», но админ может вести несколько диалогов сразу, и тогда неясно,
кому уйдёт его сообщение и какой тикет закроет `/stop`. Введено понятие
*текущего диалога*: он ставится при принятии заявки, переключается командой
`/reply 1001` и виден в `/tickets`. Ответ **reply** на пересланное сообщение
всегда уходит в тот тикет, независимо от текущего, — это самый надёжный путь,
когда диалогов много. `/stop` без аргумента закрывает текущий, `/stop 1001` —
конкретный.

**Хранение состояния админа.** Таблица `sessions` из ТЗ описывает только
пользователя, а её список состояний не покрывает ожидание причины отказа.
Добавлена таблица `admin_state` (текущий диалог + ожидаемый отказ) и
`admin_msg_map` (сообщение в чате админа → тикет) для роутинга reply.
Схемы `tickets`, `sessions`, `ticket_counter` — ровно как в ТЗ.

**Схема эволюционировала.** К `tickets` добавлены `accepted_at` (для расчёта
времени реакции), `rating` и `sla_pinged`. Миграция в `db.init()` добивает
недостающие колонки через `ALTER TABLE`, так что старая база не ломается.

**Момент выдачи номера.** Карточка подтверждения показывает `#XXXX` до отправки,
значит номер нужен раньше вставки в `tickets`. Он выдаётся атомарно на шаге
подтверждения и хранится в `sessions.ticket_id`. Если пользователь бросит
черновик, номер просто пропадёт из нумерации — это дешевле, чем показать одно
число, а сохранить другое.

## Ограничения

- Админ не может пользоваться ботом как обычный пользователь из того же чата:
  `ADMIN_CHAT_ID` целиком отдан админской панели. Для тестов флоу нужен второй аккаунт.
- Один админский чат. Для команды поддержки нужны роли и распределение тикетов.
- Сейчас бот использует long polling и рассчитан на один процесс. Для нескольких
  реплик потребуется webhook и внешняя блокировка получения обновлений.
- PostgreSQL-пул и атомарный счётчик поддерживают конкурентную работу с БД из
  нескольких обработчиков и процессов.
